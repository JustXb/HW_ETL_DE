# Итоговый отчет по построению аналитического контура и реализации etl-процесса Хамидуллина Руслана


## 1. Общая схема решения

Контур состоит из четырех связанных уровней:

1. Операционные данные звонков загружаются в YDB.
2. Yandex DataTransfer переносит таблицу из YDB в Object Storage.
3. Yandex Data Processing обрабатывает кредитные заявки под управлением Airflow.
4. Kafka topic используется для передачи JSON-событий заявок, а PySpark
   раскладывает вложенные сообщения в плоскую таблицу.
5. DataLens строит дашборды по звонкам, batch-витринам и streaming-результату.

## 2. Перенос данных из YDB в Object Storage

### Что было подготовлено

Для первого этапа использован набор данных телефонных кампаний. В нем отражены:

- идентификатор звонка;
- время звонка;
- идентификатор клиента;
- регион;
- тип маркетинговой кампании;
- статус звонка;
- реакция клиента;
- длительность разговора;
- необходимость повторного контакта.

Объем подготовленного набора составил около 31 МБ, количество строк - 269999.

### Что было сделано в YDB

В YDB создана таблица `transactions_v2`. Особое внимание было уделено полю
времени: оно подготовлено в формате, совместимом с типом `Datetime`, чтобы
импорт прошел без ошибок преобразования.

После создания таблицы данные были загружены через YDB CLI. Корректность
проверялась выборками из таблицы и подсчетом строк.

### Что было сделано в DataTransfer

В DataTransfer настроены:

- endpoint источника для YDB;
- endpoint приемника для Object Storage;
- transfer между ними.

После запуска transfer данные появились в бакете Object Storage. Это подтвердило, что перенос из YDB в объектное хранилище работает корректно.

## 3. Batch-обработка кредитных заявок

### Исходный поток данных

Для второго этапа подготовлен набор кредитных заявок. Он содержит сведения о
клиенте, регионе, продукте, запрошенной сумме, сроке, кредитном рейтинге,
уровне риска, решении по заявке, канале поступления и времени обработки.

Объем входного файла - около 55 МБ, количество строк - 480585. Это больше
требуемого минимального объема 50 МБ.

### Логика PySpark-обработки

PySpark-задание выполняет несколько аналитических преобразований:

- читает CSV из Object Storage;
- применяет фиксированную схему;
- выделяет дату события;
- формирует очищенную таблицу заявок;
- строит дневные агрегаты;
- рассчитывает показатели по уровню риска и продукту;
- считает эффективность каналов подачи заявок.

На выходе получены витрины:

- `applications_clean`;
- `daily_stats`;
- `risk_product_stats`;
- `channel_stats`.

Результаты сохранены в Object Storage в формате Parquet и зарегистрированы в
Hive Metastore через `saveAsTable(...)`.

### Управление через Airflow

Airflow DAG выполняет полный жизненный цикл временного кластера:

1. создает кластер Yandex Data Processing;
2. запускает PySpark-задание;
3. удаляет кластер после завершения обработки.

Такой подход позволяет не держать вычислительные ресурсы постоянно включенными.

### Алгоритм выполнения задания

Для запуска batch-обработки был использован следующий порядок действий:

1. В Object Storage загружается входной CSV-файл с кредитными заявками.
2. В Object Storage загружается PySpark-задание, которое будет выполнять
   обработку данных.
3. В DAG указываются параметры облачной инфраструктуры: подсеть, сервисный
   аккаунт, SSH-ключ, бакет и адрес Hive Metastore.
4. DAG загружается в директорию, подключенную к Managed Service for Apache
   Airflow.
5. После появления DAG в интерфейсе Airflow запускается DAG run.
6. Airflow создает временный кластер Data Processing.
7. На созданном кластере запускается PySpark-задание.
8. После завершения обработки кластер удаляется.
9. Результат проверяется в Object Storage по наличию Parquet-директорий с
   очищенными данными и агрегатами.

Важная часть настройки - подключение Hive Metastore. Для этого в свойствах
Spark передается URI metastore в формате `thrift://<metastore-ip>:9083`.
Благодаря этому результаты сохраняются не только как файлы в Object Storage, но
и как таблицы, доступные через Spark SQL.

### Ожидаемый результат обработки

После успешного запуска должны появиться четыре результата:

- очищенная таблица кредитных заявок;
- дневная статистика заявок;
- агрегаты по уровню риска и типу продукта;
- агрегаты по каналам поступления заявок.

Эти витрины затем используются для построения DataLens dashboard по
batch-аналитике кредитных заявок.

## 4. Streaming-сценарий с Kafka

### Назначение

Третий этап добавляет потоковую обработку. Его задача - передать JSON-события
кредитных заявок через Kafka topic, прочитать их PySpark-заданием и получить
плоскую таблицу для аналитики.

### Структура сообщения

Сообщения имеют вложенную структуру и включают:

- данные клиента;
- параметры кредитного продукта;
- скоринговую информацию;
- сведения о документах;
- статус решения;
- канал и время обработки.

Объем набора сообщений - около 22 МБ, количество сообщений - 46073.

### Обработка

Потоковая часть состоит из двух шагов:

1. запись JSON-сообщений в Kafka topic;
2. чтение topic в streaming-режиме, разбор вложенного JSON и сохранение плоской
   таблицы в Object Storage.

В результате получены поля заявки, клиента, региона, продукта, суммы, срока,
score, уровня риска, документа, статуса решения, канала и времени обработки.

### Алгоритм выполнения задания

Для streaming-части использовался следующий порядок действий:

1. В Object Storage загружается JSONL-файл с событиями кредитных заявок.
2. В Object Storage загружаются два PySpark-задания: первое для записи сообщений
   в Kafka, второе для чтения topic и разложения JSON.
3. В Managed Service for Apache Kafka создается topic для событий заявок.
4. Создается пользователь Kafka с правами на запись и чтение выбранного topic.
5. На кластере Data Processing запускается задание записи сообщений в Kafka.
   В аргументах передаются путь к входному JSONL, Kafka bootstrap servers,
   название topic, имя пользователя и пароль.
6. После успешной записи запускается streaming-задание чтения Kafka topic.
   В аргументах передаются Kafka bootstrap servers, topic, учетные данные,
   путь для результата и путь для checkpoint.
7. Streaming-задание читает сообщения, применяет схему вложенного JSON,
   раскладывает объекты и массив документов в плоский вид.
8. Результат сохраняется в Object Storage в формате Parquet.
9. Для проверки результата был подготовлен CSV-фрагмент плоской таблицы,
   который затем использовался в DataLens.

Для корректной работы streaming-задания отдельно указывается checkpoint-путь.
Он нужен Spark Structured Streaming для хранения служебного состояния и
контроля уже обработанных сообщений.

### Проверка результата

Результат считается корректным, если:

- задание записи завершилось успешно;
- задание чтения Kafka topic завершилось без ошибок;
- в Object Storage появилась директория с Parquet-результатом;
- в плоской таблице присутствуют поля заявки, клиента, региона, продукта,
  score, риска, документов и статуса решения.


К сожалению, из-за некорректной работы Яндекса большинство скриншотов сделать не удалось, так как в системе облака произошла ошибка и с моей карты списалось 13 тысяч рублей. По этой причине все использованные ресурсы были удалены, персоздавать не стал. При этом результаты обработки были сохранены в Object Storage и использованы для дальнейшей проверки.

## 5. Визуализация в DataLens

Для визуализации подготовлены три отдельных dashboard, потому что данные
относятся к разным бизнес-процессам.

### Подготовка данных для DataLens

Для DataLens использовались CSV-версии результатов. Это упростило загрузку
данных как файловых датасетов и позволило не подключать Parquet напрямую.

При создании датасетов использовались общие настройки:

- первая строка содержит заголовки;
- разделитель - запятая;
- кодировка - UTF-8;
- названия объектов в DataLens задавались без расширений файлов и без
  недопустимых символов.

После загрузки датасетов проверялись типы полей:

- числовые поля должны использоваться как числа;
- даты должны распознаваться как дата или дата-время;
- логические признаки должны использоваться как boolean;
- если DataLens определял число как строку, для графиков использовалось явное
  преобразование через `INT(...)` или `FLOAT(...)`.

### Алгоритм построения визуализаций

Работа в DataLens выполнялась по следующей схеме:

1. Создать workbook для экзаменационной работы.
2. Загрузить CSV-файлы как файловые подключения.
3. Для каждого подключения создать dataset.
4. Проверить типы полей и при необходимости поправить их.
5. Создать чарты для каждого тематического блока.
6. Собрать чарты на dashboard.
7. Добавить фильтры по ключевым измерениям.
8. Проверить, что фильтры корректно влияют на все связанные графики.

## 6. Итог

В результате работы был собран полный аналитический контур для данных кредитного
направления. Данные прошли путь от загрузки в YDB и переноса через
DataTransfer до batch- и streaming-обработки, после чего были визуализированы в
DataLens. Полученная схема может использоваться как базовый пример
интеграции нескольких сервисов Yandex Cloud в единую платформу данных.
